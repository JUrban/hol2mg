## The Multivariate number is misleading

Of the advertised 571 Multivariate-profile native proofs:

* 548 originate in Core/root HOL Light files;
* 19 originate in `Library/`;
* only **4 originate in `Multivariate/*.ml`**.

There are 11,571 public statements genuinely originating in `Multivariate/`, so current native-proof coverage of actual Multivariate material is **4/11,571**, about 0.035%.

There are also no Multivariate recorded-proof traces or `multivariate.leaves.json`. Consequently, this is not yet Multivariate proof import—it is predominantly propagation of Core proofs into the larger profile.

## The worker is partly aware of the slowdown

The transcript explicitly recognizes that full passes have grown from about 20 minutes to 42–44 minutes. It correctly attributes this to an expanding premise table being scanned while approximately 2,100 unsuccessful Core goals exhaust their budgets.

However, the worker proposes indexing only if runs exceed 50 minutes. That is too late. The architecture already needs correction:

1. **Every small lemma triggers another full-profile search.** Successful and unchanged failed goals are repeatedly reconsidered.

2. **The same work is repeated across profiles.** All 557 Core public proofs also occur in Standard, and 544 occur unchanged in Multivariate.

3. **Native facts are entered twice manually.** There are 129 theorems in `mglib/native/logic.mg`, while their statements are manually reconstructed in a large OCaml AST table in [lib/nativeproof.ml](sandbox:/workspace/scratch/879c893f19fd/repo_audit/hol2mg-20260903/lib/nativeproof.ml). The transcript records several parenthesis, binder-name, and synchronization errors resulting from this.

4. **The campaign is mostly native re-proving, not proof-guided import.** Only six current standalone proofs actually require recorded-proof leaf guidance.

5. **Generated-output churn is excessive.** Since `semantics-v1`, there have been 113 commits in three days and a diff involving roughly 1.6 million insertions and 638,000 deletions—largely repeated profile regeneration.

## Two reporting errors

The [README](sandbox:/workspace/scratch/879c893f19fd/repo_audit/hol2mg-20260903/README.md) claims 563 Core public native proofs. The real public-shard and manifest count is **557**.

The standalone native-proof directory contains 563, but six leaf-guided proofs are placed in `zz_guided.mg` and cannot currently be inlined into public shards because their dependencies may occur later in composition order. Those should be reported separately.

The README also says Multivariate has 3,305 transport-checked statements; the manifest says **3,311**.

CI currently builds and checks the ordinary translator but does not regenerate or check the `--native-proofs` outputs. Thus the green CI is meaningful, but it does not protect the main deliverable being developed on this branch.

## Recommended intervention

I would pause new theorem-by-theorem increments and ask for a short infrastructure sprint:

1. Add persistent proof-result caching keyed by statement, rules, relevant premises, and prover version.
2. Index premises by head symbol/type/constants and retry failed goals only when relevant inputs change.
3. Reuse canonical Core proofs in Standard and Multivariate instead of resynthesizing them.
4. Automatically extract native theorem statements from `.mg` files, eliminating manual OCaml AST duplication.
5. Emit guided proofs in dependency order so the six checked guided proofs can become public `Qed`.
6. Start an actual Multivariate proof-recording pilot and report results by source origin.
7. Add native-proof verification to CI and make documentation counts manifest-derived.

The long-term goal itself remains good, but its metrics should be clarified: “Multivariate progress” must mean theorems originating in `Multivariate/`, and “nice imported proof” must mean both end-to-end imported proof completion and a public native `Qed`.

So my overall verdict is: **excellent Core progress and much stronger engineering discipline, but the present brute-force loop will not scale to Multivariate. This is the right moment for an architectural optimization pass, not another dozen incremental lemma batches.**
